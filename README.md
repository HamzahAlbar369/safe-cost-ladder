# engine: deliver AI with less compute

HUMAIN × Misk Hackathon, Challenge 2. An **efficiency layer** that answers each request with the cheapest
(model, effort) configuration that still meets that task's accuracy floor and latency budget, and proves the
saving on sealed held-out data.

> **Fiction disclaimer.** The showcase workload is a motor-insurance claims desk for a *fictional* insurer ("Oasis
> Motor Insurance (fictional demo insurer)"), bilingual English / Arabic. The rules are **modelled on SAMA-issued
> instruments**: the Unified Compulsory Motor Insurance Policy, the Comprehensive Motor Insurance Rules and the
> Instructions for Motor Insurance Claims' Settlement. They are simplified, and each clause carries a source tag
> (`data/rules/SOURCES.md`). Insurer-specific values (deductibles, windows, limits) are illustrative. These are
> **not official rules and not legal advice**; the insurer and all tickets are fictional.

## The problem

Sending every request to the most capable model wastes money: most tickets are easy, and a small model answers them
correctly at a few percent of the price. The headline metric is **CPST, cost per successful task**: every dollar
spent (every call, second opinion, escalation and failed attempt) divided by the tasks answered correctly *and* within
the task's latency budget.

## Approach

- **Workload:** four task types on synthetic, rules-generated tickets: `faq`, `intent`, `extract` and `adjudicate` (a
  payout decision). One rules file (`data/rules/rules.yaml`) produces both the policy document the models read and
  the gold labels.

- **Configs:** Claude Haiku, Sonnet and Opus at effort low / medium / high (9 configs). Every config was recorded on
  every dev and shifted ticket, and any policy is evaluated by counterfactual replay of those recordings.
- **Floors first:** per-task accuracy floors and latency budgets were derived on dev and frozen (tag `floors-v1`)
  before any optimisation.
- **Policy O1** (chosen on dev, frozen at tag `freeze-v1`):
  - `faq`, `intent` and `extract` go to the cheapest config that meets their floor (all Haiku).
  - `adjudicate` runs `haiku-low ‖ haiku-medium` in parallel. The answer is accepted if it passes the checks:
    V0 valid output, V1 grounded in the ticket, V2 payout recomputes, and V3 the two Haikus agree, waiting at most
    a fixed deadline (frozen on dev) for the second opinion.
  - Otherwise O1 escalates to `opus-low`.
- **Held-out:** sealed by hash and evaluated once by `engine final`, which refuses to run unless HEAD is a clean
  `freeze-*` commit. O1 ran live; baselines and the oracle come from a 9-config held-out matrix.
- **Prompt caching:** every request carries one static system block (role, task instructions and the full policy
  document) that is cached; the ticket is the only variable part. "Cost without caching (headline)" prices every
  prompt token at the full input rate, which is conservative. "Cost with caching (actual)" is what was billed; it is
  a near-best case because the runs kept the cache warm.
- **Reported against:** baselines B1 (always-best) to B5, and an oracle (the cheapest correct config per ticket).
  Every comparison carries a paired bootstrap 95% CI.

## Live vs replayed

- **Live:** a real API call: a real answer, a real cost and wall-clock latency.
- **Replayed:** the recorded response from `cassettes/`, returned exactly as recorded (no key, no cost).
- **Simulated:** a policy scored by replaying recorded calls; O1's parallel Haiku timing is computed from calls that
  were recorded separately.

## Results

**Held-out** (400 sealed tickets, evaluated once at `freeze-v1`): O1 live costs **94.4% less per successful task** than always-best (B1), 95% CI [93.3%, 95.1%] (Cost without caching (headline)); 85.6% on Cost with caching (actual). Every per-task accuracy floor is met.

|---|---:|---:|---:|---:|---:|---|
| B1 always-best | 0.998 | 0.983 | 4.12 s | $0.03441 [$0.03384, $0.03506] | $0.00447 | met |
| B2 always-cheapest | 0.990 | 0.983 | 5.71 s | $0.00100 [$0.00097, $0.00103] | $0.00029 | met |
| B3 static per task | 0.993 | 0.988 | 4.11 s | $0.01788 [$0.01603, $0.01976] | $0.00314 | met |
| O1 (simulated) | 0.990 | 0.980 | 6.00 s | $0.00182 [$0.00157, $0.00221] | $0.00061 | met |
| **O1 (live)** | 0.993 | 0.917 | 7.19 s | $0.00194 [$0.00168, $0.00230] | $0.00064 | met |
| Oracle (cheapest correct config per ticket) | 1.000 | 1.000 | 5.41 s | $0.00120 [$0.00102, $0.00142] | $0.00032 | met |

- **Always-cheapest beat O1 on held-out.** B2 (haiku-low for everything) met every floor on held-out at CPST $0.00100 vs O1 live $0.00194, but it breached the floors on dev (accuracy 0.973), where policies were chosen, and breached them on shifted (accuracy 0.890).
- **Simulated vs live latency gap.** Live p95 7.19 s vs 6.00 s simulated; success 0.917 vs 0.980; faq ran over its latency budget live (p95 3.44 s vs 2.5 s). Correctness agreed on 395 of 400 tickets.
- **Shifted traffic** (simulated): O1 still costs 89.4% less than B1, but accuracy 0.910 vs B1 0.980; floors breached: faq, adjudicate. Fail-safe analysis (added after observing shifted): accuracy 0.945.

## Quickstart (no API key)

```
uv sync && uv run engine demo --replay
```

- **The demo** walks five dev tickets through the frozen O1 over the recorded responses in `cassettes/`, then prints
  the held-out headline table.
- `uv run engine demo --replay --verify` recomputes every metric from the committed runs (a few minutes) and checks it
  equals `reports/metrics.json`.
- `--pause` waits for Enter between tickets, for recording.
- **The report:** `uv run engine report` rebuilds `reports/report.html`, `reports/figures/*.png` and this README's
  results block. **On Windows, run `engine report` from PowerShell, not Git Bash: kaleido (the PNG exporter) hangs
  under Git Bash.** Use `--no-png` to skip the PNGs. If the PNG export ever stalls (kaleido can hang), stop it
  and run `uv run engine report --no-collect` to re-export from the saved `reports/metrics.json`.
- `uv run engine check` runs ruff, pytest, replay integrity and gitleaks.

Python 3.11+ (developed on 3.13), dependencies pinned in `uv.lock`. PNG export needs a local Chrome (kaleido).

## Run live with your own key

1. Copy `.env.example` to `.env` and set `ANTHROPIC_API_KEY` (never commit `.env`; it is gitignored).
2. **Live demo of one fresh ticket:** `uv run engine ask demo-04 --compare` prints the estimate; add `--yes` to send
   it live through the frozen O1 (and B1 with `--compare`). Five fresh tickets (`demo-01` .. `demo-05`,
   `data/demo/tickets.jsonl`, none in any evaluated split); `--rules v2` uses the policy-change document; all `ask`
   runs together are capped at $1 (run ids `demo-*`); `--replay` returns earlier recordings without a key.
3. Every paid command prints a cost estimate first and refuses to spend without `--yes` and a cap at least as large
   as the estimate. Spend is logged to `runs/spend.jsonl`.
4. Smoke test (9 configs × 5 items): `uv run engine smoke --mode live --estimate`, then the same with
   `--yes --cap-anthropic <usd>`.
5. A small live matrix on dev:
   `uv run engine matrix --split dev --subset pilot --mode auto --run-id my-pilot --repeat 7`
   (a new `--repeat` gives new request keys, so calls go live rather than replaying cassettes). Read the estimate,
   then re-run with `--yes --cap-anthropic <usd>`.
6. Held-out is sealed. `engine final` runs only at a clean `freeze-*` commit and has already been run once for
   `freeze-v1`.

## Limitations

- **Always-cheapest is competitive on held-out.** B2 (`haiku-low` for everything) met every floor on held-out and
  was cheaper than O1 (results block above). It breached floors on dev and on shifted, and O1 was chosen on dev. On
  traffic like held-out, O1's adjudicate checks are insurance that did not pay for itself.
- **Simulated parallel timing was optimistic.** In replay, O1's parallel Haiku calls are timed from calls recorded
  separately. The live held-out run had a higher p95, and `faq` ran over its latency budget live, which lowered
  live success (results block above). Latency budgets were frozen from dev replay.
- **Shifted traffic breaches two floors** (`faq` and `adjudicate`). On adjudicate no single config reaches the
  frozen floor on shifted. Nothing was retuned on shifted (D4.2). The drift monitor and the fail-safe are an
  analysis added after observing shifted; the held-out run uses the dev-frozen O1 (D4.6, D4.7).
- **Correlated verifier errors.** The checks cannot catch two Haikus that pass V0-V2 and agree on the same wrong
  answer; this happened most on shifted (report, "What didn't work").
- **Drift monitor audit sizes are totals.** In the monitor table, audit sizes are the total labelled sample across
  all tasks (stratified by task), with the faq and adjudicate counts shown per row. Detection power depends on those
  per-task counts.
- **Name collisions in the synthetic tickets.** The generator sometimes gives two people the same first name, which
  makes a few tickets ambiguous. The data were left unchanged (D2.9). See `reports/phase2/name_collisions.txt` and
  `docs/SOLVABILITY.md`.
- **Suspect shifted tickets.** A few shifted adjudicate tickets that even `opus-high` fails read, by hand, as
  generator defects (typos or contradictions on the deciding fact). They stay in the data (D4.2).
- **Verifiers V0-V2 are weak on rule-interaction errors.** They catch malformed, ungrounded or self-inconsistent
  answers, not a wrong rule applied consistently (`reports/phase2/verifiers.txt`).
- **Dev is near ceiling.** Every config is highly accurate on dev, so the floors are tight and a single ticket can
  decide whether a floor is met (see the ablations figure).
- **One recording per config.** Each (config, ticket) cell was recorded once; run-to-run variance of the models was
  not measured, and the CIs cover ticket sampling only.
- **The drift monitor needs labels.** It works on a human-labelled audit sample of recent traffic; without that
  labelling cost it cannot detect drift.
- **Routers were dropped.** A local classifier and the Jev decision model both failed the pre-registered keep/drop
  rule (D3.4). This is a negative finding.
