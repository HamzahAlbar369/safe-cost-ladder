## Name-clash audit (counts generated by `engine audit-names`, stored in `reports/phase2/name_collisions.txt`)

Two generator mechanisms put the same first name on two different people. This corrects the first version of this
note, which described only the second one.

1. **Driver lines (structural).** In `datagen/templates/render.py` every phrase for a driver other than the
   policyholder (relative, named driver, domestic worker, sponsored driver, friend, colleague) fills `{name}` from the
   caller's name slot. So in every ticket that names such a driver, the driver has the caller's first name.
   The clash is *visible* when the caller's name also appears elsewhere in the text (agent header, signature).
2. **Claimant (random).** In third-party claims the claimant's name is drawn independently from the same 20 names
   (`people()`), so it equals the caller's with probability 1/20.

The report counts, per split: tickets with a named non-insured driver; those whose gold depends on who was driving
(denied for an unauthorised driver, or payable because the driver is authorised); how many of those have a visible
clash; and the same for the claimant clash. Held-out is audited in-process and reported as counts only; dev and
shifted list ids. It also compares dev accuracy on the visible-clash tickets with the other adjudicate tickets, per
model family. Because the relationship is stated in words ("a colleague", "my brother"), most readers resolve the
clash; the visible-clash tickets with a deny-by-unauthorised-driver gold are the risky ones (dev-0378 is one).

## Decision (Hamzah, Phase 2 sign-off): no data change

Leave the frozen data (including the sealed held-out) unchanged and document the limitation here and in the README.
Alternatives considered: making `other_i != name_i` and giving drivers their own name pool would regenerate every
split, re-seal held-out and force re-recording of the changed dev cells.
